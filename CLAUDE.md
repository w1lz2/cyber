# Контекст проекта

## Задача
Следить за появлением свободных окон записи в Посольство Молдовы в РФ (сервис Reservio)
и присылать в Telegram только НОВЫЕ окна (отмены чужих записей и новые открывшиеся дни).
Плюс кнопки в Telegram: «ближайшая запись» (самое раннее окно) и «проверить сейчас» (все свободные окна)
в любой момент.
Нужно на срок меньше месяца, работать должно на сервере без ПК пользователя.
Пользователь общается по-русски.

## Как устроено
- `monitor.py` — один файл, только `requests`. Браузер не нужен.
- Источник данных — внутренний JSON:API сайта (проверено в браузере 27.10.2026, работает без cookies/авторизации):
  - `GET https://ambasada-r-moldova-in-f-rusa.reservio.com/api/v2/businesses/09250556-2450-437f-aede-82e78712f114/availability/booking-slots?filter[from]=YYYY-MM-DD&filter[to]=YYYY-MM-DD&filter[serviceId]=<id>&ignoreBookingBoundaries=0`
    → `data[]` типа `timeSlot`: `attributes.start` (ISO, +03:00), `relationships.resource.data.id` (сотрудник).
    Возвращает ТОЛЬКО свободные слоты. Без `filter[resourceId]` — сразу по всем сотрудникам. Широкий диапазон дат работает.
  - `.../availability/booking-days?...` → `bookingDay` с `attributes.date`, `isAvailable`.
  - `.../resources` — сотрудники (id → name), `.../services` — услуги.
- Услуга по умолчанию: «Изготовление паспорта (загран)» `59c845fa-48c9-4f79-b7b2-1d07f895f2e6`.
  Сотрудники по ней: Владимир Руснак `b6eae6ed-86ac-4ed7-9fe5-2482f0d0bcb9`, Дойна Гайтур `eb4e43fe-9b6d-4dfd-99ad-451ca81bb630`.
- Запись открыта на 30 дней вперёд (на 27.10 — окна 17–26.11, ~283 шт.).
- Состояние — `state.json`: `slots` (ключ слота `"Имя|YYYY-MM-DDTHH:MM"`), `fails`, `alerted`,
  `empty_count`, `last_ok`, `tg_offset` (позиция в очереди обновлений Telegram), `kb` (версия клавиатуры).
- Первый запуск шлёт сводку (+ постоянную клавиатуру); дальше — только новые слоты;
  новые дни помечаются «🆕 новый день». После 3 ошибок подряд — предупреждение, после восстановления — сообщение.
- Защита от сбоя: если сайт вдруг вернул 0 окон (а было ≥10), не верим, пока 0 не подтвердится 3 проверки подряд,
  иначе после сбоя все окна пришли бы как «новые».

## Telegram-бот (long polling, `getUpdates`)
- Между плановыми проверками процесс ждёт нажатий (`getUpdates` с timeout ≤50 с) — ответ сразу.
- Клавиатура под полем ввода: «⏰ Ближайшая запись» (свежая проверка + самое раннее будущее окно, другие времена
  того дня, ближайшее у других сотрудников), «🔍 Проверить сейчас» (свежая проверка + полный список, новые помечены 🆕),
  «ℹ️ Статус». Команды `/nearest`, `/check`, `/status` (регистрируются через `setMyCommands`).
  Любой другой текст в личке → справка. Нажатия «ближайшая» и «проверить» в одной пачке → одна проверка сайта.
- Клавиатура версионируется (`KB_VERSION`, в state.json — `kb`): при изменении MAIN_KEYBOARD увеличить версию,
  бот сам пришлёт новые кнопки пользователям (иначе у них останутся старые).
- Inline-кнопки: «🔄 Обновить» (callback `check` / `nearest`), «🔍 Все окна» (callback `check`) и «📝 Записаться» (URL).
- Если новое окно — самое раннее из всех, в уведомлении «⏰ Это теперь ближайшая запись».
- Прошедшие слоты отбрасываются сразу в `get_free_slots`.
- Отвечает только чатам из `TG_CHAT_ID` (можно несколько через запятую); уведомления — всем им.
- Повторные нажатия в одной пачке обновлений выполняются один раз.
- Два экземпляра бота одновременно → 409 Conflict от Telegram (пишется в лог).
- Сообщения в HTML (`parse_mode`), имена экранируются. Токен вырезается из текстов ошибок (`redact`).

## Режимы запуска
- `python monitor.py` — одна проверка + ответ на накопившиеся нажатия
- `python monitor.py --for 330` — 330 минут: проверка каждые INTERVAL_MIN (1) минут + бот,
  раз в 30 мин коммитит state.json (для GitHub Actions)
- `python monitor.py --loop` — бесконечно (VPS / Railway)
- Без `TG_TOKEN`/`TG_CHAT_ID` — одна пробная проверка с выводом в лог, state.json не пишется
  (в Actions — `::warning::` про секреты). Удобно проверить, отвечает ли сайт с серверов GitHub.

## Переменные окружения
`TG_TOKEN`, `TG_CHAT_ID` (обязательно), `STAFF` (имена через запятую, пусто = все),
`SERVICE_ID`, `DAYS_AHEAD` (90), `INTERVAL_MIN` (1), `STATE_FILE` (state.json).

## Деплой
- GitHub Actions: `.github/workflows/monitor.yml` — job крутит `--for 330`, cron `*/20` + concurrency
  ставит следующий запуск в очередь → проверка каждую минуту без перерывов. Репозиторий публичный (w1lz2/cyber).
  (Изначально был cron */5 — GitHub запускал его редко, пользователь пропускал окна.)
  checkout с `ref: github.ref_name` — иначе запуск из очереди берёт state.json на момент постановки в очередь
  (устаревший) → повторные уведомления и конфликт при push. При push `git pull --rebase -X theirs`
  (побеждает свежий локальный state.json).
- Railway (альтернатива, пробные $5/30 дней): `railway.json` → `python -u monitor.py --loop`.
  Если запущен Railway — workflow на GitHub нужно отключить, иначе дубли уведомлений и 409 у бота.

Сценарии: первый запуск, новые окна, повторная отмена, кнопки (проверка, ближайшая, статус), чужой чат, offset,
сбои/восстановление, пустой ответ, длинные сообщения, обновление клавиатуры, цикл `--for`.

Запускать после любых правок monitor.py.
